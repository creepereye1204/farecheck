# eval.md — 완료 기준과 평가셋

POC의 목적은 개발계획서에 넣을 **"기술 검증 완료" 숫자**를 만드는 것이다. 숫자는 이 문서의 방식으로만 낸다.

## 1. 평가셋 (30건)

| 구분 | 건수 | 만드는 법 |
|---|---|---|
| 정상 | 12 | 실제 서울 구간(관광지↔숙박 밀집지역↔공항)을 카카오 경로로 조회 → 상한의 60~95% 금액으로 영수증 생성 |
| 확인 필요 | 8 | 상한의 110~140% 금액, 또는 통행료 불일치, 또는 미터기 미사용 |
| 명백한 초과 | 10 | 상한의 2~16배 금액 5건 + 할증 규칙 위반(주간 심야할증, 서울 내 시계외할증) 5건 |

- 영수증 이미지는 **합성**한다. 2025년 12월 이후 한·영 병기 영수증의 항목 구성(최종 요금, 승하차 시각, 할증 여부, 통행료)을 따르되, 실제 회사 로고나 실제 차량번호는 쓰지 않는다. 차량번호는 형식만 맞춘 가짜 값.
- 실제 영수증을 구할 수 있으면 개인정보를 가린 뒤 추출 평가에만 추가한다.
- 각 케이스는 `eval/cases/{id}.json`에 정답(추출 필드, 출발/도착, 기대 등급, 기대 근거 코드)을 둔다.
- 경로 응답은 한 번 조회한 뒤 fixture로 고정한다. 평가 재현성을 위해 실시간 조회를 하지 않는다.

## 2. 지표와 합격선

| 지표 | 정의 | 합격선 |
|---|---|---|
| **오고발률** | 정답이 NORMAL인데 CLEAR_EXCESS로 판정한 비율 | **0% (필수)** |
| 등급 정확도 | 기대 등급과 일치한 비율 | ≥ 90% |
| 명백한 초과 재현율 | 정답 CLEAR_EXCESS 중 CLEAR_EXCESS로 판정한 비율 | ≥ 90% |
| 금액 추출 정확도 | `total_fare` 정확히 일치 | ≥ 95% |
| 시각 추출 정확도 | `ride_start`, `ride_end` 분 단위 일치 | ≥ 90% |
| 응답 시간 | `/api/judge` p95 (LLM 설명 포함) | ≤ 10초 |

등급 정확도는 두 가지로 따로 낸다: (a) 추출을 정답 필드로 대체한 경우(엔진 단독), (b) 추출부터 전체 파이프라인. 계획서에는 둘 다 쓴다.

## 3. 실행
```
python eval/run_eval.py --cases eval/cases --out eval/report.md
```
`eval/report.md`에는 지표 표, 틀린 케이스 목록(케이스 id, 기대/실제 등급, 원인 분류: 추출 오류/규칙 오류/경로 오류), 실행 일시, `rule_version`을 남긴다.
